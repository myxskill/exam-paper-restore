# 现场笔记：为什么"擦掉手写"经常做不成，以及怎么判断

> 本文件是踩坑记录与判别标准。SKILL.md 只讲流程，细节都在这里。
> 遇到"到底能不能自动擦"的判断犹豫时，读本文件。

---

## 一、核心事实（先接受它，再动手）

**手机照片里，"学生手写"与"印刷体"经常在三个维度上完全重叠。**

一份真实五年级数学卷的实测数据（3000×3786 手机照片，学生用深色中性笔）：

| 判别维度 | 印刷体 | 手写体 | 差值 | 能否分离 |
|---|---|---|---|---|
| 颜色 B/G/R | 106.2/108.7/117.2 | 109.5/112.0/119.8 | 2~3 | ❌ 等于噪声 |
| 灰度均值 | 111.0 | 114.0 | 3 | ❌ 纸面起伏就有这么大 |
| 灰度 P25 | 94.6 | 94.0 | 0.6 | ❌ |
| 笔画半宽(dt 中位) | 1.97 | 1.40 | 反向且重叠 | ❌ 且方向不稳定 |
| 蓝笔判据 B−R > 25 | — | 命中 **0** 像素 | — | ❌ 根本不是蓝笔 |

结论：**没有可用的"分离开关"。** 此时任何自动分离都会啃掉印刷体，硬做就是负优化。

同一批数据里，**红笔批改**却能被干净剔除（掩膜覆盖率 1.5%~1.8%，印刷体完好）——
因为红笔是彩色的，颜色维度天然可分。这就是"红笔能自动去、手写往往不能"的根本原因。

## 二、决策表（diagnose_ink.py 会直接给结论）

| 结论 | 触发条件 | 做法 |
|---|---|---|
| `SEPARABLE_BY_COLOR` | 手写区蓝笔像素占比 > 0.35 且印刷区 < 0.05；或手写彩度比印刷高 20 以上 | `separate_ink.py --by color`，基本无损 |
| `MAYBE_BY_GRAY` | 灰度 P25 差 ≥ 25 或均值差 ≥ 30（手写明显更浅/更深，如铅笔、淡墨） | `separate_ink.py --by gray --lo --hi`，**必须逐处放大复核** |
| `MAYBE_BY_STROKE` | 笔画粗细差比 > 50% 且绝对差 > 0.6 | 风险高（粗体印刷字会被一起吃掉），建议直接走交互擦除 |
| `NOT_SEPARABLE` | 三维全落在噪声量级 | **不要自动擦**，交付 `eraser_tool.html` 让用户交互擦除 |

**判定必须配 `*_diag_zoom.jpg` 目视确认**：先确认坐标框住的确实是那一类内容，
再看数字。本次实测就出现过"以为框的是手写、其实框的是印刷体"（`HAND` 框里显示的是"的17份"印刷字），
若不看图直接信数字，会得出完全错误的结论。

## 三、环境与工具坑（每一条都真实踩过）

### 1. Windows 中文路径 → `cv2.imread` 直接返回 None
`cv2.imread` / `cv2.imwrite` 在 Windows 上处理不了含中文的路径，**不报错，只是返回 None**，
后续会在无关的地方炸出难以理解的异常。
→ 统一用 `_common.imread_u` / `imwrite_u`（`np.fromfile` + `cv2.imdecode` / `cv2.imencode` + `tofile`）。

### 2. 朝向：**不要默认 180°**
手机拍的折叠试卷，"一张纸的正反面各拍一次、每张图里左右两页并排"是常态，
正确朝向往往是 **顺时针 90°**。本次两张图都是 cw90，一开始按 180° 处理导致所有坐标全错、
连"哪边是手写"都判断反了，白跑了好几轮。
→ **任何坐标分析之前先跑 `orient_check.py`**，出四方向联系表，挑"所有文字水平可读"的那格。

### 3. 红笔判据用"绝对阈值"会翻车
纸张偏暖/发灰时，`redness = R-(G+B)/2 > 8` 会把整张纸算成红笔，
实测掩膜覆盖 **18%**，印刷体被啃掉。
→ 必须用**相对局部纸面的增量**：`A*` 通道偏离 128 超过 k，且红度相对大核中值背景的增量超阈值。
`remove_red.py` 已内置，且会打印覆盖率并对 >12% / <0.02% 报警。

### 4. 红笔很淡时（手机拍照常见）
实测 `A*-128` 的 P99 只有 5.0、红度相对增量 P99 只有 7.5 —— 红笔非常淡。
纯颜色提取会勉强，但配合修复填充，目视仍然干净。
→ `remove_red.py` 会先打印"红度体检"，P99 < 12 时会提示把 `--k` 收到 7~9 并目视复核残留。

### 5. AI 影像擦除模型对"试卷"是负优化
实测 `buddy-image-processing --operation erase`：
- **几乎没动手写部分**（手写答案原封不动）
- 分辨率从 3000×3786 压到 1760×2336
- 宽高比从 0.792 变成 0.753（变形）

对"要重新打印的试卷"而言这是纯负优化。**别把它当方案。**

### 6. 开运算（形态学）按粗细分离不可靠
手写笔画通常更粗（实测 dt 中位 2.0 vs 印刷 1.4），但**粗体印刷标题的粗细与手写重叠**，
k=3..11 逐档试过，无法在"吃掉手写"和"保住粗体标题"之间找到可行点。
且这个信号方向不稳定 —— 另一次实测手写反而更细（1.40 vs 1.97）。

## 四、交付策略：先给预期，再给三条路

**不要把"我做不到"当结论抛给用户**，也不要假装做到了。按这个顺序交付：

1. **能自动做的先做扎实**：转正 + 去红笔（确定性，质量高）。
2. **把不可自动化的部分变成"一分钟能做完的手工活"**：交付交互擦除工具 + 干净底图。
3. **给出更优路径**（按优先级）：
   - **有空白原件** → `align_subtract.py` 对齐相减。**唯一能做到印刷体一个像素都不动**的解法。
   - **能按印刷内容重排版** → 重排一份可打印的干净空白卷（版式不会 100% 一致）。
   - **只有这一张填过的图** → 交互擦除工具。

用表格把"哪个维度能不能分"摆出来，用户会立刻理解难点在哪，
而不是觉得"AI 怎么这么笨"。

## 五、SOP 清单

```
[ ] 1. 列出输入图片，记录张数/尺寸/体积（>10MB 先降采样再处理）
[ ] 2. orient_check.py → 看联系表 → 确定 correct rotation（别默认 180°）
[ ] 3. remove_red.py --rotate <正确方向> --split <页数>
[ ] 4. 放大核对：红笔压在印刷体上的区域，印刷线有没有被啃断
[ ] 5. diagnose_ink.py --grid → 读坐标 → 填 regions.json
[ ] 6. diagnose_ink.py --regions → 看 *_diag_zoom.jpg 确认坐标框对了内容 → 读结论
[ ] 7. 按结论分支：
       可分离  → separate_ink.py，再逐处复核
       不可分离→ 复制 assets/eraser_tool.html 到交付目录，指导用户交互擦除
[ ] 8. 有空白原件 → align_subtract.py --detect-only 先验配准，再出图
[ ] 9. 交付：底图 + 工具/成品 + 一句实话（哪部分自动做了、哪部分需要手动）
```

## 六、容易被忽略的两个细节

- **`regions.json` 的坐标是"转正后"的**。文件里的 `rotate` 字段与命令行 `--rotate` 不一致时，
  `diagnose_ink.py` 会警告，别忽略这个警告 —— 方向不一致意味着坐标全错。
- **`align_subtract.py` 出图后要看印刷线条有没有重影**。有重影 = 配准没对准，
  多半是空白件太模糊或拍得角度差太多，换一张空白件比调参数有效。
